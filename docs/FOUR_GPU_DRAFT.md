# 4 GPU並列化の実装と未検証事項

この変更は静的なコード確認のみで、テスト・実GPUでの検証・実制作での速度測定は行っていない。

- 採用話題をクリップごとに待ち行列へ入れ、今回の制作で共通の最大4 GPU枠を使う。文字起こしが終わると、空いた枠へ待機中の5本目・6本目を投入する。
- 字幕整文は60秒に分割せず、1話題1回の要求を選定本数に応じて並列に実行する。6話題なら最大6件で、音声が認識されなかった話題は要求しない。要求と時刻の記録は話題別に残す。
- 文字起こし・描画は同じ4 GPU枠を共有する。準備済みの描画を空いた枠へ投入し、その時点で2本準備できていれば同じGPUで最大2本を同時に描画する。GPUのセッション数・メモリ・CPU・ネットワークによって失敗や低速化もあり、速度は未測定。
- 各クリップの描画後すぐに個別の非公開Releaseへ保存する。制御側はその記録を監視して、完了本数・クリップ番号・描画時間をActionsログに出力する。
- 文字起こしが終わったクリップから整文・描画へ進め、他のクリップの終了を待たない。待機中の文字起こしはGPU確保の優先対象とする。
- 話題選定用の音声窓は最大2つを並行して準備し、窓ごとの準備時間を記録する。
- 完成分は `tools/collect_production_clip.py` で全体の終了前に回収できる。途中回収した完成動画は最終回収時に再ダウンロードしない設計。
- 話題またはクリップが4件未満の場合は、その件数が並列数の上限となる。単一の話題・クリップは分割しない。制作と無関係な別ジョブが使うGPU数はこの枠に含まれない。
- render-onlyの既存経路は並列化していない。
- 途中失敗時も保存済みの個別クリップは残り、個別回収できる。整文まで全件完了した後に描画が失敗した場合は、保存済みクリップを部分結果Releaseにまとめ、明示的なrender-onlyの `--reuse-render` で再利用する設計。文字起こし・整文が未完の失敗や強制中断では、部分統合が行われない場合があり、自動再開はしない。送信・実行が不明な要求は自動再送しない。
- 部分描画の依頼マーカーと結果Releaseは再送防止・復旧のため保持する。後片付けの手順は未整備。
- GPU割当数はColabの実際の容量に左右され、4台の確保は保証されない。

実制作での性能や安全な復旧を確認するには、同一性、並列時の要求記録、GPU解放、部分失敗・中断からの復旧、保存と統合、実際の割当とNVENC並列数を含む検証が必要。
