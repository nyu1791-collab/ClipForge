# 準備と転送の重複削減

対象は検証ブランチのみ。動画再生成、GPU起動、Actionsによる実機監査・全量読み戻しは実行していない。

| 対象 | 以前 | 改修後 |
|---|---|---|
| 正常描画の成果物 | GPU→一時Release→Actions本体回収→再梱包→最終Release→監査用全量再取得 | GPU→最終Release。Actionsは小さな実行記録だけ取得 |
| Release保存監査 | 別Pythonで全量再取得・サイズ/SHA走査 | なし。アップロード完了を記録 |
| 同じRelease取得 | 保存先一覧やprivate属性の照会が重複 | 取得情報を引き渡して同じ照会を省略 |
| OSとPython準備 | 順番に実行 | 並列。両処理が終わったら描画へ進む |
| チャット用依存 | 毎回導入 | chat_panel=trueの場合のみ |
| 分割転送の梱包 | 全量tarを書いて、もう一度読んでチャンク化 | tarを直接チャンクへ出力 |
| Drive転送前 | 動画全体の取得後にGoogleへの接続処理 | 設定済み認証・保存先作成後に動画を取得 |
| Driveの再確認 | プロフィール照会・本体再ハッシュなど | 削除。読み戻し監査もなし |

約500MBの描画バッチでは、GPUから最終保存までの動画転送を4回から1回に減らす構成。端末への実回収、Driveへ送るための取得・アップロードは別で、必要な時点に行う。削減量は転送経路の構造からの計算で、実測の短縮秒数ではない。

Release転送メタデータはschema 2。ZIP本体とtransfer.jsonの2アセットを保存し、transfer.jsonへrequest receipt・stage manifest・GPU実行記録を同梱する。大容量アーカイブの追加走査をしない。schema 1の過去成果物は読み取り可能。実施していない検証の成功表示はしない。

保存失敗や処理失敗を成功とする変更ではない。アップロードコマンドの終了、工程の完了／失敗、依頼と成果物を結ぶ情報は通常の処理結果として使用する。展開先パスの処理は維持する。GPU解放も行う。

YouTube/Twitch/Kick/直接HTTPSのURL取得を維持。ASR再利用、5本以上・各5分以上、品質監査なし、承認待ちなし、失敗後の自動再生成なしを継続。

小さな合成データでストリーム梱包と新形式の受け渡しをローカル実行。実動画の監査、全件テスト、実機速度再計測は行っていない。38秒だった前回のRelease保存や37.82秒だったColab準備が短縮対象だが、改修後の時間は未測定。
